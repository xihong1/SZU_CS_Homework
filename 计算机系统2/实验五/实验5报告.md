> **2、测量Cache层次结构和容量的代码**
>
> ```c
> #include <windows.h>
> #include <stdlib.h>
> #include <stdio.h>
> #include <string.h>
>
> #define NUM_ITERS 100
>
> void test_cache_levels_random() {
>     int i, iter;
>     LARGE_INTEGER frequency, start, end;
>     double elapsed;
>     long long total = 0;
>
>     QueryPerformanceFrequency(&frequency);
>
>     printf("=== Cache Level Detection (Random Access) ===\n");
>     printf("Size (KB) | Time (s) | Time/access (ns)\n");
>
>     int sizes_kb[] = {4, 8, 16, 32, 48, 64, 96, 128, 192, 256, 384,
>                       512, 768, 1024, 1536, 2048, 3072, 4096, 6144,
>                       8192, 12288, 16384, 24576, 32768, 65536, 131072};
>
>     for (i = 0; i < sizeof(sizes_kb)/sizeof(sizes_kb[0]); i++) {
>         int size = sizes_kb[i] * 1024;
>         int num_accesses = size / 64;
>         int *indices = (int*)malloc(num_accesses * sizeof(int));
>         char *array = (char*)malloc(size);
>         int j;
>
>         memset(array, 1, size);
>         for (j = 0; j < num_accesses; j++) indices[j] = j;
>         for (j = num_accesses - 1; j > 0; j--) {
>             int k = rand() % (j + 1);
>             int tmp = indices[j]; indices[j] = indices[k]; indices[k] = tmp;
>         }
>
>         total = 0;
>         QueryPerformanceCounter(&start);
>         for (iter = 0; iter < NUM_ITERS; iter++)
>             for (j = 0; j < num_accesses; j++)
>                 total += array[indices[j] * 64];
>         QueryPerformanceCounter(&end);
>         elapsed = (double)(end.QuadPart - start.QuadPart) / frequency.QuadPart;
>
>         printf("%9d | %8.6f | %15.2f\n",
>                sizes_kb[i], elapsed,
>                (elapsed * 1e9) / (num_accesses * NUM_ITERS));
>         free(array); free(indices);
>     }
> }
>
> void test_cache_line_size() {
>     int sizes[] = {16, 32, 48, 64, 80, 96, 128, 256, 512, 1024, 2048, 4096};
>     int s, i, iter;
>     LARGE_INTEGER frequency, start, end;
>
>     QueryPerformanceFrequency(&frequency);
>     printf("=== Cache Line Size Test (Stride) ===\n");
>     printf("Stride (B) | Time (s)\n");
>
>     for (s = 0; s < sizeof(sizes)/sizeof(sizes[0]); s++) {
>         int stride = sizes[s];
>         int array_size = 64 * 1024;
>         char *array = (char*)malloc(array_size);
>         long long total = 0;
>
>         memset(array, 1, array_size);
>         QueryPerformanceCounter(&start);
>         for (iter = 0; iter < 10000; iter++)
>             for (i = 0; i < array_size; i += stride)
>                 total += array[i];
>         QueryPerformanceCounter(&end);
>         double elapsed = (double)(end.QuadPart - start.QuadPart) / frequency.QuadPart;
>         printf("%10d | %8.6f\n", stride, elapsed);

>     }

> **图1、矩阵乘法性能对比可视化**（见 `matrix_benchmark.png`）
>
> 左图为不同矩阵大小下两种算法的执行时间对比柱状图，右图为优化加速比曲线图。
>
> 加速比定义：加速比=优化前系统耗时/优化后系统耗时；
>
> 所谓加速比，就是优化前的耗时与优化后耗时的比值。加速比越高，表明优化效果越明显。
>
> 分析原因：
>
> 原始矩阵乘法代码A采用经典的三重循环 i-j-k 顺序进行计算。在计算 `c[i][j]` 时，内层循环遍历 `a[i][k]`（行优先，空间局部性好）和 `b[k][j]`（列优先，空间局部性差）。当矩阵较大时，`b[k][j]` 的访问跨距为整个矩阵的行宽，导致频繁的Cache Miss。以 float 类型（4字节）为例，当矩阵大小为1000时，单个矩阵占 4MB，远超L1 Cache（32KB），`b[k][j]` 的列访问几乎每次都产生Cache Miss。
>
> 优化算法采用**分块（Tiling/Blocking）**技术，将大矩阵划分为 `BLOCK_SIZE=64` 的小块进行计算。每个小块大小为 64×64×4 = 16KB，可完整放入L1d Cache（32KB）中。这样，在计算每个小块时，`a` 和 `b` 的对应子矩阵块能够驻留在Cache中，极大减少了Cache Miss次数。
>
> 从数据可以看出，当矩阵较小时（100），数据整体可放入Cache，两种算法差异不大（加速比仅1.28x）。随着矩阵增大（1500→2500），原始算法的Cache Miss急剧增加，而分块算法通过将工作集限制在Cache范围内，加速比显著提升至2.57x。在3000时，即使分块算法的单个块能放入L1，但总数据量（3×36MB=108MB）远超L3 Cache（64MB），导致部分数据必须从主存读取，加速比回落至1.95x。
>
> **2、测量分析出Cache 的层次结构、容量以及L1 Cache行有多少？**
>
> **1. 实验原理**
>
> Cache是位于CPU和主存之间的小容量高速存储器。现代x86处理器通常采用多级Cache层次结构（L1、L2、L3），每级容量递增但速度递减。CPU访问数据时，首先查找L1 Cache，若命中则直接读取；若未命中则依次查找L2、L3，最后访问主存。
>
> 测量Cache容量的基本方法是：分配不同大小的数组，对每个数组进行随机访问（以打乱硬件预取器的预测），并记录访问时间。当数组大小小于某级Cache容量时，数据完全在该级Cache中，访问延迟较低且稳定；当数组大小超过该级Cache容量时，部分数据被驱逐到下一级存储，导致访问延迟出现明显跳变。通过观察延迟随数组大小变化的"拐点"，可以推断各级Cache的容量。
>
> 测量Cache Line数量的方法类似：在固定大小的数组中，以不同的步长（stride）进行访问，观察当步长超过Cache Line大小时性能的变化。
>
> **2. 测量方案及代码**
>
> 测量方案：
> - 分配大小从4KB到128MB的数组
> - 对数组索引进行随机打乱（Fisher-Yates shuffle），确保访问顺序随机
> - 每个数组大小重复100次随机访问并累加
> - 使用Windows高精度计时器 `QueryPerformanceCounter` 记录时间
> - 计算每次访问的平均延迟（纳秒）
>
> 完整代码见上文。

> **4. 分析过程**
>
> **Cache层次结构分析：**
>
> 从表2的随机访问测试数据中，可以清晰地观察到三个明显的延迟"拐点"：
>
> - **第一阶段（4KB ~ 768KB）**：访问延迟稳定在 **0.91~1.05ns**。这表明数据完全在 **L1 Data Cache** 中。L1 Cache容量为每核32KB，但由于L2 Cache（每核1MB）可以作为L1的后备缓冲，所以直到约768KB时延迟仍然保持在较低水平。
>
> - **第二阶段（1024KB ~ 12288KB）**：访问延迟跳升至 **1.34~1.86ns**。1024KB（1MB）正好是每核L2 Cache的容量。当数组超过1MB后，部分数据必须从L2 Cache中驱逐到L3 Cache，导致延迟增加。整个阶段延迟保持在1.3~1.9ns，说明数据主要在 **L2 Cache** 中命中。
>
> - **第三阶段（16384KB ~ 24576KB）**：访问延迟进一步跳升至 **3.31~7.10ns**。16MB是每核可使用的L3 Cache容量上限。当数组超过16MB后，越来越多的数据需要从共享的 **L3 Cache** 中读取，延迟再次增加。
>
> - **第四阶段（32768KB及以上）**：访问延迟稳定在 **11~12ns**。当数组大小超过L3 Cache容量后，数据必须从 **主存（DRAM）** 中读取，延迟显著增加并趋于稳定。DRAM的访问延迟约为L1 Cache的12~13倍。
>
> **L1 Cache Line分析：**
>
> 从表3的步长测试中可以看出：
>
> - 当步长为16、32、48字节时，执行时间较长（0.031s、0.015s、0.011s），因为每个Cache Line（64字节）中有效数据的比例较低（25%、50%、75%），导致更多的Cache Line被加载但未充分利用。
> - 当步长为64字节时，执行时间降至0.008s，此后随步长增大，执行时间继续降低（因为总访问次数减少），但**每个有效访问的效率**趋于稳定。
> - 步长从48→64时，执行时间出现明显的比例跳变（10.7ms→8.1ms），这正是步长跨越 **64字节Cache Line边界** 的特征。

> 由于采用了顺序页访问方式，硬件页表 walker 和 L2 TLB（2048条目，覆盖8MB）能够有效隐藏TLB Miss的开销。从数据中可以看到，时间随页数线性增长，没有出现明显的延迟跳变。这说明在当前测试范围内（最大32768页=128MB），TLB Miss的惩罚被成功掩盖。对于更精确的TLB测量，需要采用随机跨页访问方式，使硬件预取器和页表 walker 无法有效工作。·

> **六、实验改进思想**

> **1. 矩阵乘法优化的改进思路**

> **（1）问题发现与分析**

> 在实验初期，直接运行原始代码A时发现：当矩阵大小超过500后，执行时间急剧增加，远超理论计算量应有的耗时。通过分析访问模式发现：
> - 矩阵A的访问 `a[i][k]` 是行优先，空间局部性好
> - 矩阵B的访问 `b[k][j]` 是列优先，每次内层循环k迭代时，访问地址跳跃一整行（size×4字节），导致严重的Cache Line浪费
> - 以1000×1000矩阵为例，每次访问B的不同列元素都需要加载新的Cache Line，Cache Miss率接近100%

> **（2）优化方案选择**

> 考虑了多种优化方案后，选择了**分块（Tiling）**技术，原因如下：
> - **分块（Tiling）**：将大矩阵分解为小块，使每个块的工作集能放入Cache，是最直接有效的Cache优化方法
> - **循环交换（Loop Interchange）**：将i-j-k改为i-k-j，虽能改善B的访问局部性，但会破坏A的局部性，效果有限
> - **寄存器分块（Register Tiling）**：进一步将小块映射到寄存器，可获得更高加速比，但实现复杂度较高

> **（3）分块大小的选择**

> 分块大小 `BLOCK_SIZE` 的选择是关键：
> - 理论上，块大小应满足：`3 × BLOCK_SIZE² × sizeof(float) ≤ L1d_Cache_Size`
> - 对于32KB的L1d Cache：`3 × BLOCK_SIZE² × 4 ≤ 32768`，解得 `BLOCK_SIZE ≤ 52`
> - 实际选择 `BLOCK_SIZE=64`（16KB/块），略微超出L1d但仍在L2范围内，综合考虑了计算效率和Cache容量
> - 实验验证：分别测试了BLOCK_SIZE=32、64、128，发现64在多数矩阵大小下表现最优

> **2. Cache测量的改进思路**

> **（1）对抗硬件预取器**

> 初始方案采用顺序访问，但发现延迟曲线几乎线性，无法区分Cache级别。原因是现代CPU的硬件预取器能预测顺序访问模式，提前将数据加载到Cache中。
>
> **改进措施**：采用Fisher-Yates洗牌算法随机打乱访问顺序，使预取器无法预测，从而暴露出真实的Cache访问延迟差异。

> **（2）防止编译器优化**

> 使用 `-O0` 编译选项禁止编译器优化，防止循环被展开或向量化，确保测量结果反映真实的Cache行为。

> **（3）多次迭代取平均**

> 每个数组大小进行100次完整遍历，取总时间计算平均延迟，减少系统调度、中断等随机因素的干扰。

> **3. 未来可进一步改进的方向**

> - **SIMD向量化**：使用AVX-512指令集对分块算法进行向量化，可进一步提升2-4倍性能
> - **多线程并行**：使用OpenMP将外层循环并行化，充分利用16核CPU的并行能力
> - **预取指令**：手动插入 `_mm_prefetch` 指令，提前将下一块数据加载到Cache
> - **非Temporal存储**：对结果矩阵C使用 `_mm_stream_si128` 绕过Cache直接写入主存，减少Cache污染
> - **TLB测量改进**：采用随机跨页访问（而非顺序访问），使页表 walker 无法有效工作，从而观测到TLB Miss的真实开销

> **七、实验结论**
>
> 1. **Cache访存模式对性能有显著影响**：普通矩阵乘法因列优先访问矩阵B导致严重的Cache Miss，采用分块（Tiling）优化后，将工作集限制在L1 Cache大小（16KB/块），加速比在2500×2500矩阵时达到最高2.57x。分块大小的选择应与L1 Cache容量匹配。
>
> 2. **实验测得本机Cache层次结构**：
>    - **L1 Data Cache**：32KB/核，访问延迟约0.9~1.0ns
>    - **L2 Cache**：1MB/核（共16MB），访问延迟约1.3~1.9ns
>    - **L3 Cache**：64MB共享（每CCD 32MB），访问延迟约3~7ns
>    - **主存（DRAM）**：访问延迟约11~12ns，是L1的约12倍
>
> 3. **Cache Line大小为64字节**，通过步长测试验证。当访问步长从48字节增加到64字节时，Cache Line利用效率出现明显跳变。
>
> 4. TLB测量受限于测试方法，顺序访问模式下TLB Miss被硬件优化掩盖。AMD Ryzen 9 7945HX的L1 dTLB为64条目（4KB页），L2 TLB为2048条目。
